# CBOM Clean-Room Provenance Ledger

Every shipped CBOM capability MUST trace to a row here. The "evidence" column is a public
spec/behavioral source (docs, papers, CycloneDX schema, tool OUTPUT) — **never copied source code**.
The "our re-implementation" column is our ORIGINAL design. This ledger is the audit trail proving the
product is clean-room: it studies OSS tools' behavior and re-implements techniques, and ships no OSS
BOM tool. OSS tools appear only as benchmark oracles in `bench/cbom/`.

### The clean-room rule model we will encode (the C1–C3 / C14 backbone)

Sonar's engine is **language-agnostic rules + per-language AST translators**: a rule names an *entry-point
library symbol*, and the entry point — not the algorithm token — fixes the primitive **context/kind**
(cipher / digest / signature / MAC / key-agree / KDF / DRBG / protocol); params (key size, mode, padding,
curve) bind from the call's arguments. Our clean-room design re-implements this WITHOUT an AST-DSL port:

- **Rule corpus = data** (`rules.py`): a list of `CryptoRule{library, lang_scope, symbol_pattern,
  primitive_context, algorithm_key?, param_extractors}`. The algorithm may be fixed by the symbol
  (`hashlib.md5`→md5) or read from an argument (`Cipher.getInstance("AES/CBC/PKCS5Padding")`→algo+mode+pad).
- **Detection = match symbol_pattern on a code line, then bind params** (today line-regex; C13 adds intra-file
  dataflow for cross-statement binding; C1's AST upgrade is the longer arc). The primitive *role* comes from
  the rule's `primitive_context`, so the same `"SHA-256"` token resolves to a **hash** under
  `MessageDigest.getInstance` but to a **signature** component under `Signature.getInstance("SHA256withRSA")`.
- **Provenance**: every asset is stamped `crypto:detectedBy=<library>` + a confidence, so benchmark parity
  can attribute a miss/extra to a specific library rule (and C11's executability layer can down-weight).

### What the current PQC lane does vs the PQC universe (the evidence gap)

`rules.py` marks RSA/ECC/DH/DSA `quantum_vulnerable=True` and **all** symmetric/hash `False`; `pqc.py`
grades only the vulnerable-asymmetric assets → `nistQuantumSecurityLevel=0`, a primitive→migration-target
map, and **one flat timeline string** ("deprecate 2030 / disallow 2035, SP 1800-38 / IR 8547"); raises one
`QUANTUM_VULNERABLE` flag (warning/Medium). `algorithm_scan` detects the PQC *family tokens*
(Kyber/ML-KEM, Dilithium/ML-DSA, SPHINCS+/SLH-DSA) but `pqc.py` never grades them. Verified gaps:

- **`nistQuantumSecurityLevel` semantics (row 19):** the field is the NIST PQC category **0–6**, not a
  binary — AES-128-GCM is **level 1** in the CycloneDX example, RSA-against-quantum is **0**. We set it
  on **nothing but vulnerable asymmetric**, so AES-256 / SHA-384 / ML-KEM-1024 are ungraded.
- **PQC param-set category (row 20):** ML-KEM-512/768/1024 = Cat 1/3/5, ML-DSA-44/65/87 = Cat 2/3/5,
  SLH-DSA-128/192/256 = Cat 1/3/5. We detect the **family** but not the **param set**, so we can't grade
  the category or test CNSA-2.0 sufficiency (which mandates the Cat-5 sets only and *excludes* 512/768/44/65).
- **Grover / quantum-weakened symmetric + HNDL (row 21):** Shor breaks asymmetric (→0); Grover only
  *halves* symmetric — AES-128 → ~64-bit, below the CNSA-2.0 AES-256 floor; SHA-1/SHA-256-for-long-term
  below the SHA-384 floor. We mark all symmetric/hash `False` with no below-floor distinction, and have
  **no harvest-now-decrypt-later** concept on the data a quantum-vulnerable key-establishment protects.
- **Hybrid + stateful-HBS (row 22):** X25519MLKEM768 / SecP256r1MLKEM768 / X448MLKEM1024 hybrids and
  LMS/XMSS/HSS (SP 800-208, firmware-signing scope) are **undetected** — a hybrid handshake mis-reads as
  plain X25519 (false-positive quantum-vulnerable) and a stateful firmware signer inventories nothing.
- **CNSA 2.0 timeline + roadmap (row 23):** CNSA 2.0 is a *category-phased* mandate (SW/FW-signing 2030,
  web/cloud & OS & niche 2033, network 2030, 2027 NSS-acquisition gate); IR 8547 deprecates 2030 /
  disallows 2035. We carry **one flat string for every asset**, no per-use-case deadline, no roadmap
  aggregation, and **CNSA 2.0 is absent from the compliance lane**.

### What the current compliance lane does vs the R5 framework list (the evidence gap)

`cbom/compliance.py` (C7) ships **5** graph-queried tri-state frameworks — `nist_1800_38b` (PQC-1..4),
`nist_800_57` (KM-1..6), `omb_m_23_02` (OMB-1..3), `eu_cra` (CRA-1..3), `eu_dora` (DORA-1..3) — all reusing
the AIBOM tri-state machinery (`register_check`/`register_applicability`/`run_framework`, coverage =
pass/(pass+fail), `_has_crypto` applicability → out_of_scope on a crypto-free repo). The single asymmetric
floor is `_MIN_ASYMMETRIC_BITS = 2048` (`undersized_keys`). R5's named list is **8** frameworks. Verified
state per framework:

- **NIST SP 1800-38B/C (row 27):** 38B (discovery/inventory/risk-prioritization) is already mapped by
  `nist_1800_38b` PQC-1/2/3 — **confirmed sound**. 38C is **interop + performance lab testing** = manual /
  not_bom_evidenceable → **NO new framework**; at most a one-line manual req parallel to PQC-4. Negative
  finding recorded so no later iteration spawns a phantom `nist_1800_38c` build story.
- **NIST SP 800-57 / OMB M-23-02 / EU CRA / EU DORA (row 28):** all four existing frameworks' checks
  **re-confirmed** against primary sources (SP 800-131A Rev.2 / SP 800-57 Pt.1 Rev.5 / OMB memo / Reg (EU)
  2024/2847 Annex I / Reg (EU) 2022/2554 Art.9). No new work.
- **FIPS 140-3 (row 24):** ABSENT from the lane. FIPS 140-3 lists no algorithms itself — the approved set is
  SP 800-140C/D + SP 800-131A Rev.2. The lane has a negative weak-list but **no positive approved-algorithm
  allow-list** and no Ed25519-approved-but-X25519-KAS-not / approved-curve distinction. → **C20 (NEW)**.
- **PCI-DSS 4.0.1 (row 25):** ABSENT. The "Strong Cryptography" glossary def (≥112-bit *effective* strength,
  industry-tested only) + Req 4.2.1 transmission-cert trust tied to PCI requirement numbers are not modelled.
  → **C21 (NEW)**.
- **BSI TR-02102 (row 26):** ABSENT — and the highest-value gap. BSI's **RSA/DH ≥ 3000-bit** floor is
  strictly stricter than the lane's only floor (NIST-2048): a repo that PASSES `nist_800_57` KM-2 can FAIL
  BSI. Brainpool-curve preference, SHA-256 hash floor, AES-only symmetric, and the TLS-PFS mandate are all
  absent. → **C22 (NEW)**.
