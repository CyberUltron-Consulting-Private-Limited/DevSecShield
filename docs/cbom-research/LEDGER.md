## R1 gap-list — where DevSecShield's CBOM lane is weaker than IBM/PQCA CBOMkit (evidence-backed)

Ordered by leverage. Each maps to a story (existing Cx or newly-appended C10/C11).

1. **Detection is regex-on-a-line, not receiver+argument-aware.** sonar-cryptography binds a *specific API method* to its *ordered arguments* and resolves nested/referenced values into a semantic tree. We match bare algorithm tokens per line. → **C1** (rule model), extended intra-file binding in **C1/C2**.
2. **Python-centric corpus.** Real coverage of Java (JCA/BouncyCastle), Go (`x/crypto`), Node/WebCrypto, RustCrypto/ring, .NET crypto API surfaces is missing. → **C1/C2/C3**.
3. **No OID enrichment.** CBOMkit injects algorithm OIDs + default params at enrichment; our assets carry no `oid`. → **C10 (new)**.
4. **No crypto-policy config-file scanning.** `java.security` disabled-algorithm policy and `openssl.cnf` cipher/TLS-min config are first-class theia signals; we read protocols only from source. → **C11 (new)**.
5. **Narrow related-crypto-material coverage** vs theia's Gitleaks-driven key/material discovery (kept deliberately narrow, but broadenable). → **C6**.
6. **No untrusted/problematic-CA signal** on certificates (we have self-signed/weak-sig/expiry). → **C4 (extend)**.
7. **Where we are already at-or-ahead:** hand-built CycloneDX 1.6 crypto-asset emission (C4/C9), tri-state graph-queried compliance across NIST/OMB/EU frameworks (C7) is broader than CBOMkit's single quantum-safe allowlist policy, deterministic PQC grading with migration targets (C6), and source-level TLS/protocol + weakness inventory (C3/C5) — cbomkit-theia is a *filesystem* scanner and structurally cannot see source crypto usage, so our `OurUnique` is large by design (documented in `bench/cbom`).

## Architecture notes (for downstream BUILD stories)
- CBOMkit is 5 layers: **sonar-cryptography** (source AST, Java/Python/Go), cbomkit-lib, cbomkit-action (CI), cbomkit (REST/UI/compliance), **cbomkit-theia** (Go CLI, filesystem/container). Only the two *scanners* are technique sources; the app/CI layers are not.
- sonar-cryptography pipeline: **AST match → Detection Store tree → Mapping to INode semantic model (algorithm/key/mode/padding/digest) → Enrichment (OID + defaults) → CycloneDX 1.6 output** with evidence + dependency relationships. Our lane mirrors detect→normalize→emit; the missing middle pieces are argument binding (C1) and OID enrichment (C10).
- cbomkit-theia merges into a source CBOM via `CBOM.merge()`; its plugins are certificates / secrets / javasecurity / opensslconf / problematicca / keys / vex. We already cover certificates + keys + protocols from source; javasecurity + opensslconf (config policy) and problematicca are the concrete deltas.
- C/C++ AST is explicitly *not* supported by sonar-cryptography (open issue #374, would need sonar-cxx) — so our planned C/C++ coverage (C3) is a place we can **exceed** the oracle, tracked as OurUnique.

### R2 clean-room DETECTION-RULE MODEL design (the keystone C1 implements)

A `CryptoRule` is a plain frozen data record (dict/dataclass literal), **not** a fluent-builder object (that is the sonar-cryptography behavior we learned from, re-expressed as OUR data structure):

```
CryptoRule(
  lang,          # python|java|go|javascript|c|rust|dotnet
  library,       # asset-map key: pyca|jca|bouncycastle|go-stdlib|x-crypto|node-crypto|webcrypto|ring|rustcrypto|dotnet|openssl|libsodium
  receiver,      # regex/token the call's receiver must match (algorithms|hashlib|Cipher|crypto/aes|crypto.subtle|EVP|System.Security.Cryptography) — may be None
  method,        # regex/token for the call/ctor/fn (AES|getInstance|NewCipher|createCipheriv|Aes256Gcm|EVP_aes_256_gcm|Aes.Create)
  arg_roles,     # ordered tuple of roles bound positionally to the call's args:
                 #   ALGORITHM | KEY_SIZE | MODE | CURVE | PADDING | DIGEST | TRANSFORM_STRING | WEBCRYPTO_ALGOBJ | LITERAL_KEY
  primitive,     # fixed CycloneDX primitive if the API pins it, else resolved from the ALGORITHM arg
  name,          # fixed canonical key OR a resolver fusing matched groups + resolved args
)
```

Matching is a bounded **3-step per file** (no full AST, no network, deterministic):
1. **Prose-strip + call-split** — reuse `_strip_noncode` (blank docstrings/`/* */`), then a shallow paren-balanced splitter captures `(receiver, method, [args])` from `receiver.method(a,b,..)` / `method(...)` shapes (crypto usage is single-call-per-line in practice; no need for a real parser).
2. **Data-flow-lite symbol table** — one pass records `name → value` (crypto literal / int key-size / mode enum / byte-length). When an `arg_role` value is a bare identifier, resolve it here (last-assignment-wins, intra-file, no control-flow).
3. **Rule apply** — for each captured call, select rules whose `receiver`+`method` match; bind `arg_roles` to args (resolving vars via step 2); emit ONE `crypto:` fact carrying primitive + resolved keySize/mode/curve/padding. `TRANSFORM_STRING` handling: JCA `"AES/GCM/NoPadding"`→{algo,mode,padding}; Node `"aes-256-gcm"`→{algo,keysize,mode}; signature `"SHA256withRSA"`→ digest+pke (two facts + a `signs-with` edge). `WEBCRYPTO_ALGOBJ` reads the `{name,hash,namedCurve,modulusLength}` object literal.

The per-language rule TABLES are OURS, keyed to each ecosystem's public API surface (rows above). Rollout mirrors R1's plan: Python rule table first (C1, proves the model on the existing fixture), then Java+Go (C2), then JS/TS+C/C+++Rust+.NET (C3). Library→asset maps land per-language and the manifest parsers consolidate in C12.

### R2 gap-list — where our multi-language detection is weaker than sonar-cryptography (evidence-backed, leverage-ordered)

1. **Detection is a flat `(key, line-regex)` tuple, not a receiver+method+arg-role rule record.** `AES` on any line is `AES`; no method binding, no arg-position semantics, no dependent-value resolution. → **C1** (rule model + data-flow-lite symbol table).
2. **Python-only library/API coverage.** Java JCA/BouncyCastle, Go stdlib+x/crypto, Node/WebCrypto, C/C++ OpenSSL/libsodium, Rust RustCrypto/ring, .NET have NO API rule sets (some are only disambiguation hints; `.cs` isn't even a scanned extension). → **C1/C2/C3**.
3. **No transformation-string decomposition.** JCA `"AES/GCM/NoPadding"`, Node `"aes-256-gcm"`, signature `"SHA256withRSA"` all carry algo+mode+padding+digest in ONE string we never split. → **C2/C3**.
4. **Library→asset maps ride only `requirements.txt`/`pyproject.toml` + Python imports.** No pom.xml/go.mod/package.json/Cargo.toml/csproj manifest parsing. → **C12 (new)**.
5. **Where we will EXCEED the oracle (OurUnique by design):** C/C++ OpenSSL/libsodium (sonar issue #374 has no C/C++), JS/TS WebCrypto, Rust RustCrypto **including ml-kem/ml-dsa PQC**, and .NET — none are in sonar-cryptography's Java/Python/Go tree. Track these as large `OurUnique` in `bench/cbom`, not misses.

### R2 architecture notes (for C1/C2/C3/C12)
- sonar-cryptography ships per-language modules (Java, Python, Go) each = detection rules + an AST translator + a check registrar bound to the SonarQube language plugin; it does **not** support JS/C/Rust/.NET today. Our lane deliberately covers those four as OurUnique (no SonarQube, our own lightweight call-splitter instead of per-language ASTs).
- Bundle ids `Jca` (standard JCA) vs `Bc` (BouncyCastle) drive their per-library translation — our analogue is the `CryptoRule.library` tag, which also selects the library→asset label.
- Node `crypto` names are OpenSSL cipher strings (`aes-256-gcm`), so the SAME `TRANSFORM_STRING` splitter serves Node AND the C/C++ OpenSSL EVP name decomposition (`EVP_aes_256_gcm`) — one clean-room helper, two ecosystems.
- .NET needs `.cs`/`.vb`/`.fs` added to `LANGUAGE_EXTENSIONS`; that is the ONLY language-detection change (the rest is a rule table). Weak-primitive .NET classes (`TripleDES/DES/RC2/Rijndael/MD5/SHA1`) feed the EXISTING C5 weakness lane unchanged (they normalize to keys already in `rules.WEAK_ALGORITHMS`).
