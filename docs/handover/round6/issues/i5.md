**What happens:** the scan-node gate (`netutil.resolve_checked`) applies the never-scan list per resolved address. When a name resolves to several addresses, it drops the excluded ones and connects to whatever is left.

**Why it matters:** customers list a host's address in never-scan to keep it out of scope, for example `10.0.0.5` for a production database. On a dual-stack network the same machine also answers on IPv6 (for example `db.internal` → `10.0.0.5` and `fd00::5`). Today the scan goes ahead over IPv6 to the very host the customer excluded. The runner showed exactly this: `localhost` → `127.0.0.1` (excluded) + `::1`, and the node connected to `::1`.

**Expected:** if any address a name resolves to is on the never-scan list, skip the whole name and report it as `skipped_never_scan`. This is the conservative reading of "never scan". The same rule applies to redirect targets.

**Fix:**
- in `resolve_checked`, refuse the name when any resolved address matches;
- restore the test to list only `127.0.0.1`, so it is the regression test for dual-stack names;
- add a unit test with a name that resolves to an excluded IPv4 address and a non-excluded IPv6 address.
