ITERATION (C2 — certificate + related-crypto-material scanner): LANDED. New files: aibom/src/aibom/cbom/x509.py (pure-stdlib DER/ASN.1 X.509 reader) + scanners/certificate_scan.py + tests/test_cbom_certificate_scan.py; registered in cbom/scanners/__init__.py. All 8 C2 tests + 20 CBOM tests + ruff(scoped) + mypy GREEN. KEY GOTCHA: the aibom package ships INTENTIONALLY-LIGHT deps — `cryptography`/`pyOpenSSL` are NOT installed (they're only scan TARGETS in the fixture). So x509 parsing MUST be hand-rolled stdlib; do NOT `import cryptography` in product code. The DER reader extracts subject/issuer CN, self_signed (raw issuer-TLV == subject-TLV bytes), notBefore/notAfter (UTCTime YY>=50→19YY per RFC5280), signatureAlgorithm OID->name, and RSA modulus->keySize; parse_certificate() is TOTAL (returns None, never raises) so a malformed/non-cert file can't crash a scan. SPKI gotcha: the pubkey OID is nested INSIDE the AlgorithmIdentifier child of SubjectPublicKeyInfo, not a direct child. Cert props use crypto:notValidBefore/notValidAfter/subjectName/issuerName/selfSigned/signatureAlgorithm/publicKeyAlgorithm/keySize (mirrors CycloneDX certificateProperties for the C4 emitter). Related-crypto-material: scans RAW source text (NOT _strip_noncode) for inline PEM key blocks so the hardcoded PRIVATE KEY inside crypto_app.py's triple-quoted string IS caught; materialKind in CycloneDX relatedCryptoMaterialType enum (private-key/public-key/secret-key/initialization-vector/salt). IV/salt detection is deliberately NARROW (named-var = bytes/hex literal assignment only) so it yields 0 on the fixture (manifest has no IV/salt) and stays honest. SAME pre-existing chroma differential failures as C1 (crewai miss, [chroma-provider]/[chroma-framework]) — they exercise scan_repo, my scanner is CBOM-only (CBOM_SCANNERS, never SCANNERS; asserted by a test). ITERATION (C3 — protocol/TLS scanner): LANDED. New files: aibom/src/aibom/cbom/scanners/protocol_scan.py (order=30, name=crypto_protocol) + tests/test_cbom_protocol_scan.py (9 tests); registered in cbom/scanners/__init__.py. All 9 C3 + 29 CBOM tests + scoped ruff + mypy(73 files) GREEN. KEY DESIGN: emits ONE `protocol` crypto_asset per (protocolType, file) — multiple version tokens in one file (the fixture's `"TLSv1.0"` literal AND `ssl.TLSVersion.TLSv1`) COLLAPSE to a single asset carrying the WEAKEST (min) version, so tls_config.py yields exactly one TLS 1.0 asset, not two/three. Props mirror CycloneDX protocolProperties: crypto:protocolType (tls/ssh), crypto:protocolVersion ("1.0"), crypto:cipherSuite ("ECDHE-RSA-AES128-SHA"), crypto:strength ("weak" for TLS<1.2 / any SSL — the inventory signal C5 reads; C3 emits NO flags, lane discipline). GOTCHAS: (1) MUST strip prose like the algorithm lane — `_strip_prose` blanks triple-quotes/`/* */` AND per-line `#`/`//` comments, because tls_config.py's comment `# below the TLS 1.2 floor` would otherwise inventory a phantom TLS 1.2 (my version regex allows TLS-space-1.2). C-comment strip uses `(?<!:)//` so `ssh://` survives. (2) Version regex `\bTLS[._]?v?1(?:[._]([0-3]))?\b` deliberately does NOT match `PROTOCOL_TLS_CLIENT` (no version digit) — generic TLS *use* (SSLContext/PROTOCOL_TLS*/set_ciphers/wrap_socket/create_default_context) is a SEPARATE trigger that emits a versionless asset. (3) Cipher regexes avoid the `TLS_CIPHERS`/`TLS_CLIENT` variable-name trap: OpenSSL form needs >=2 hyphen groups (so `AES-256` isn't a suite), IANA form needs a real `WITH`/AES/CHACHA20 token. SSH lane (paramiko/SSHClient/ssh://) yields 0 on the fixture (no SSH tokens) keeping protocols count == manifest's 1. Same pre-existing chroma differential failures unrelated. KEY MAPPINGS (crypto: prop -> CycloneDX 1.6 cryptoProperties): assetType<-crypto:assetType (the spec REQUIRES it; bom-1.6.schema.json cryptoProperties.required=[assetType]); algorithmProperties.primitive<-crypto:primitive (scanner already emits valid enum values pke/hash/block-cipher/...), parameterSetIdentifier<-crypto:keySize (NOT a "keySize" field — CycloneDX folds key length into parameterSetIdentifier), curve<-crypto:curve, mode<-crypto:mode LOWERCASED + enum-mapped via _CDX_MODE (scanner emits UPPER "GCM"/"ECB"; XTS->other since not in spec enum {cbc,ecb,ccm,gcm,cfb,ofb,ctr,other,unknown}); certificateProperties.{subjectName,issuerName,notValidBefore,notValidAfter} (crypto:signatureAlgorithm/publicKeyAlgorithm/keySize/selfSigned have NO certificateProperties home — signatureAlgorithmRef wants a bom-ref not a name — so they stay in properties[] only); relatedCryptoMaterialProperties.type<-crypto:materialKind; protocolProperties.{type,version,cipherSuites:[{name:<crypto:cipherSuite>}]}. nistQuantumSecurityLevel: C4 emits it for quantum-vulnerable assets as level 0 (a quantum-vulnerable PKE has no quantum security) by reading crypto:quantumVulnerable=="true", AND passes through an explicit crypto:nistQuantumSecurityLevel if present — so C6 (PQC grading, depends C4) just enriches the property + adds migration-target props; emitter needs no change.
