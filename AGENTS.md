# DevSecShield BOM scanners — conventions

- Scanners self-register via a registry pattern; adding a scanner/reporter/check/scan-level is ONE file.
- ScanResult { components, edges, flags, scores, compliance } flows scanners → scorer → checks → reporters. Graph helpers: by_ref / out_edges / neighbors.
- Healthcare/crypto-specific data goes in namespaced `properties` (clinical:/regulatory:/dataset:/crypto:), never non-spec top-level keys.
- CycloneDX is hand-built (AIBOM modelCard; CBOM crypto-asset). Validate every emitted BOM against its bundled schema in CI — a schema-invalid BOM is a build failure.
- Frontend: reuse the existing scanner components, theme tokens, chart library, and severity palette. The existing SBOM/SAST/DAST pages are the style authority.
- Compliance verdicts are tri-state: OUT_OF_SCOPE / NOT_BOM_EVIDENCEABLE / pass-fail. Coverage% = pass/(pass+fail); the other two are reported as their own counts.
- Enrichment is deterministic (known-model KB + regex/AST); the product ships NO runtime LLM. A provider interface allows adding the Anthropic API or Bedrock later — but product code must not call an LLM unless a story enables it. (Claude Code's OAuth login is the agent, unrelated to the product.)

## Discovered conventions / gotchas (append below)
- The standalone AIBOM engine lives at `aibom/` (uv package, src layout). The locked finding schema is STRICT — `test_every_finding_matches_the_locked_finding_schema` fails on any extra key; to exclude something from the dashboard drop it from the findings LIST (the adapter's `_inventory()`), never tag the finding.
- `aibom emit` CLI scans at LEVEL 1; the product runs at LEVEL 4 (`scan_to_devsecshield(level=4)`). A new deep scanner (cloud-iac, code-import) at level ≥2 won't affect the L1 emit goldens but DOES affect L4 (dashboard, benchmark, differential test).
- `model_refs.py` (MODEL_RE) is the model-id allowlist regex; `parsers/code_imports.py` (AI_IMPORTS) is the curated import allowlist — redis is deliberately omitted (it's a general datastore; adding it regresses test_license_resolver by flagging redis-as-cache in chroma).
- Two implementers shared branch `ansh`; coordinate before commits. The 71 MB chroma fixture is a gitignored upstream clone (absent in CI → differential/compliance chroma cases self-skip).
- Bench is ISOLATED (`aibom/bench/`, never product). Bedrock for the Cisco oracle: `us-east-1` + `global.anthropic.claude-haiku-4-5-20251001-v1:0` (the `apac` default id is invalid in this account).
- CBOM ground-truth fixture: `aibom/tests/fixtures/synthetic-crypto-app/` + `expected_crypto.json` (the CBOM oracle, mirrors CycloneDX 1.6 crypto-asset assetTypes: algorithm|certificate|protocol|related-crypto-material; each algorithm carries `weak` + `quantum_vulnerable` booleans). `cert.pem` is a REAL openssl self-signed RSA-2048 cert (so C2 can parse real expiry). Manifest consistency is gated by `test_crypto_fixture_manifest.py` — a self-consistency test only (no CBOM scanner until C1+ reconciles `RabbitMQ/worker/helpers/tools/cbom_agent/`).
- `conftest.py` `collect_ignore=["fixtures"]` excludes scan TARGETS from pytest collection — a new fixture tree won't be picked up as a test, and a manifest test must live in `aibom/tests/` (not under fixtures/).
- KNOWN PRE-EXISTING failures when run locally with the chroma clone present: `test_differential.py::test_recall_threshold[chroma-provider]` and `[chroma-framework]` (missed crewai). These self-skip in CI (chroma clone gitignored/absent). Don't chase them inside an unrelated story — confirm a failure is yours by stashing your changes and re-running.
- KNOWN PRE-EXISTING ruff baseline: ~29 E501 line-length errors live in existing `tests/` files (present even with your changes stashed). Don't let them block your story — scope ruff to your own files (`ruff check src/aibom/cbom ...`); your additions must be 0-error. mypy is fully clean — keep it that way.
- The CBOM lane is a PEER of the AIBOM scan lane, NOT part of it. It lives at `aibom/src/aibom/cbom/` (rules.py + registry.py + pipeline.py + scanners/). It reuses the same `ScanContext` + `Scanner` base + `ScanResult` model but registers into its OWN list (`CBOM_SCANNERS` via `@cbom_register`) so CBOM scanners NEVER run inside `scan_repo` (which would pollute AIBOM emit goldens/differential). Entry point: `aibom.cbom.pipeline.scan_crypto(path) -> ScanResult`. It does NOT call the AIBOM scorer/OWASP mapper (CBOM scorer is C8).
- Crypto assets use ONE component kind `crypto_asset` (CycloneDX `cryptographic-asset`, in `KIND_TO_CDX`). ALL crypto detail lives in `crypto:` namespaced `properties` (assetType/primitive/keySize/mode/curve/strength/quantumVulnerable) — never new top-level model fields. The C4 emitter reads those properties to build `cryptoProperties`.
- CBOM detection is RECONCILED (not rebuilt) from the worker `cbom_agent`: the algorithm tables/normalization/ambiguity-gating are ported into `aibom/cbom/rules.py`. The ADDED piece is per-usage parametrization — `extract_key_size/mode/curve` pull params off the SAME source line, so RSA-2048≠RSA-1024 and AES-GCM≠AES-ECB. The fixture's `algorithms.TripleDES` line IS the manifest's "DES" (the F3 manifest test maps DES→"TripleDES"); the C1 test matches DES on family, not exact name.
- C2 GOTCHA — NO `cryptography` in product code: the `aibom` package ships intentionally-light deps (`pydantic`/`typer`/`jsonschema`/`referencing`/`pyyaml` only). `cryptography`/`pyOpenSSL` are NOT installed — they appear only as scan TARGETS in the fixture. So X.509 parsing is a hand-rolled pure-stdlib DER/ASN.1 reader at `aibom/cbom/x509.py` (`parse_certificate(der)->Certificate|None`, TOTAL — returns None on garbage, never raises, so a malformed cert in a scanned repo can't crash the scan). It captures subject/issuer CN, self_signed (raw issuer-Name-TLV bytes == subject-Name-TLV bytes), notBefore/notAfter (UTCTime YY≥50→19YY per RFC 5280 §4.1.2.5.1), signatureAlgorithm OID→name, and RSA modulus→keySize. ASN.1 nesting gotcha: the public-key OID lives INSIDE the AlgorithmIdentifier child of SubjectPublicKeyInfo, not a direct SPKI child.
- C2 lane: `cbom/scanners/certificate_scan.py` (order=20) emits TWO assetTypes — `certificate` (from .pem/.crt/.cer/.der files + inline `BEGIN CERTIFICATE` blocks) and `related-crypto-material` (private/public keys + narrow hardcoded IV/salt/secret-key literals). Cert props mirror CycloneDX `certificateProperties` so the C4 emitter reads them straight: `crypto:notValidBefore/notValidAfter/subjectName/issuerName/selfSigned/signatureAlgorithm/publicKeyAlgorithm/keySize`. Material props: `crypto:materialKind` (CycloneDX relatedCryptoMaterialType enum). CRITICAL: related-material scans RAW source text (NOT `_strip_noncode`) so a hardcoded PRIVATE KEY inside a triple-quoted string literal (crypto_app.py) IS caught — the OPPOSITE of the algorithm lane which must blank docstrings. IV/salt detection is deliberately narrow (named-var=bytes/hex-literal assignment only) → 0 on the fixture (manifest has none), keeping counts honest.
- C3 lane: `cbom/scanners/protocol_scan.py` (order=30, name=`crypto_protocol`) emits `protocol` crypto_assets — ONE per (protocolType, file). Multiple version tokens in the SAME file collapse to a single asset carrying the WEAKEST (min) pinned version (the fixture's `"TLSv1.0"` literal + `ssl.TLSVersion.TLSv1` → one TLS 1.0 asset, not two). Props mirror CycloneDX `protocolProperties`: `crypto:protocolType` (tls/ssh), `crypto:protocolVersion`, `crypto:cipherSuite`, `crypto:strength` (weak for TLS<1.2 / any SSL — the C5 inventory signal; C3 emits NO flags). MUST `_strip_prose` (triple-quotes + `/* */` + per-line `#`/`//`) like the algorithm lane, else the fixture's `# below the TLS 1.2 floor` comment inventories a phantom TLS 1.2 (the version regex allows `TLS<space>1.2`). C-comment strip uses `(?<!:)//` so `ssh://` survives. The version regex does NOT match `PROTOCOL_TLS_CLIENT` (no digit); generic TLS *use* (`SSLContext`/`PROTOCOL_TLS*`/`set_ciphers`/`wrap_socket`/`create_default_context`) is a SEPARATE trigger emitting a versionless asset. Cipher regexes dodge the `TLS_CIPHERS`/`TLS_CLIENT` var-name trap: OpenSSL form needs ≥2 hyphen groups (`AES-256` is not a suite), IANA form needs a `WITH`/AES/CHACHA20 token. SSH lane (paramiko/SSHClient/ssh://) → 0 on the fixture (no SSH tokens), keeping protocols == 1.
- C4 emitter: the CBOM CycloneDX 1.6 crypto-asset serializer lives in the SHARED `aibom/src/aibom/emit/cyclonedx.py` (NOT a separate CBOM emitter) — the emitter is the RENDER lane and renders whatever components a `ScanResult` carries, so `emit_cyclonedx(scan_crypto(path))` produces a valid CBOM through the SAME `emit_and_validate`/`validate_cyclonedx` build-failure path. `_emit_component` routes `comp.kind == "crypto_asset"` to `_emit_crypto_asset` ABOVE the `KIND_TO_CDX` fallback; crypto LIBRARIES (FrameworkComponent w/ `crypto:role=library`) stay `type: library`. crypto:->cryptoProperties map: `assetType`<-crypto:assetType (spec REQUIRES it); algorithm: `primitive`<-crypto:primitive (scanner emits valid enum), `parameterSetIdentifier`<-crypto:keySize (CycloneDX has NO keySize field — key length folds into parameterSetIdentifier), `curve`, `mode`<-crypto:mode LOWERCASED+enum-mapped (`_CDX_MODE`; XTS->other), `nistQuantumSecurityLevel` (see below); certificate: subject/issuer/notValidBefore/notValidAfter only (signatureAlgorithm/publicKeyAlgorithm/keySize/selfSigned have no certificateProperties home — `signatureAlgorithmRef` wants a bom-ref, not a name — so they remain in properties[]); related-crypto-material: `type`<-crypto:materialKind; protocol: type/version/`cipherSuites:[{name:<crypto:cipherSuite>}]`. nistQuantumSecurityLevel rule (`_nist_quantum_level`): explicit `crypto:nistQuantumSecurityLevel` passthrough else quantum-vulnerable->0 — so C6 (PQC grading) enriches the PROPERTY + adds migration-target props and the emitter needs NO change. The bundled bom-1.6 schema carries the FULL cryptoProperties $defs with `additionalProperties:false` everywhere → any stray/misspelled cryptoProperties field is a build failure; raw `crypto:` props are ALSO carried through as `properties[]` (a component may have both cryptoProperties + properties) so the dashboard reads one consistent place.
- C1 GOTCHA: prose must NOT be scanned. `_strip_noncode()` blanks triple-quoted docstrings + `/* */` blocks (preserving line count) BEFORE per-line algorithm regexes run — without it a docstring like "RSA-2048, AES-256-GCM" produces phantom assets (key-size/mode bleed across algorithms on the line). Only LINE-EXPLICIT key sizes fold into a display name; table-default sizes (3DES=168) stay in the property only. C1 emits components ONLY (no flags — weak-flagging is C5).
