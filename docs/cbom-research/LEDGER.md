# CBOM Clean-Room Provenance Ledger

Every shipped CBOM capability MUST trace to a row here. The "evidence" column is a public
spec/behavioral source (docs, papers, CycloneDX schema, tool OUTPUT) — **never copied source code**.
The "our re-implementation" column is our ORIGINAL design. This ledger is the audit trail proving the
product is clean-room: it studies OSS tools' behavior and re-implements techniques, and ships no OSS
BOM tool. OSS tools appear only as benchmark oracles in `bench/cbom/`.

## Rules
- No reading-and-pasting OSS source. Learn from docs, papers, schema, and observed output only.
- OSS tools run ONLY in `bench/cbom/` as oracles; never on the product import path.
- Each BUILD story updates its row to `implemented` with the product file path + bench oracle delta.

## R1 gap-list summary (what CBOMkit / cbomkit-theia / Sonar-Cryptography do that we don't yet)
1. **Cross-call dataflow** (Sonar rule-dependencies) → **C13**: link a separately-defined key size / curve to the cipher/signature that consumes it; split composed transformation strings.
2. **OID enrichment** (Sonar enricher) → **C10**: deterministic algorithm→OID KB; emit `cryptoProperties.oid` so assets canonicalize on OID (parity + dedup with the oracle).
3. **Environment-restriction executability** (theia java.security + opensslconf) → **C11**: parse `jdk.tls.disabledAlgorithms` / `openssl.cnf`; mark detected assets non-executable + confidence + `DISABLED_BY_POLICY`.
4. **Problematic/known-bad-CA trust** (theia problematic-CA) → **C12**: known-bad-CA KB; `UNTRUSTED_CA` flag; self-signed-in-prod severity in the cert lane.

These four are appended to `prd.json` as build stories C10–C13 (each depends on R1 + the relevant inventory
story). B1 (extend oracles + baselines) now also depends on C10–C13 so the differential gate measures every
new capability before the CI lock (B2). Architectural parity rows (5/6/9/10) confirm the current lane already
matches or exceeds the oracle; only the gap rows (2/3/7/8) spawn new build work.
